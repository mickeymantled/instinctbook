# docs/openapi — generated, do not hand-edit

Everything in this directory is generated by `apps/api/src/openapi/generate.ts` from the Zod
schemas `apps/api` validates requests and responses with (docs/SPEC.md "Reliability contract":
"OpenAPI 3.1 is generated from the same schemas used at runtime"). It is committed so the API
contract is reviewable in a diff and so `apps/api` can serve it at `GET /openapi.json` without
generating it at request time.

**Do not hand-edit any file here.** A hand edit is exactly what `pnpm openapi:check` exists to
catch — the next regeneration overwrites it silently, and the drift check fails loudly in the
meantime.

## Files

- `openapi.json` — the full OpenAPI 3.1 document, exactly what `GET /openapi.json` serves.
- `schemas/<Name>.schema.json` — one standalone JSON Schema (draft 2020-12) per Zod schema
  registered with a stable `.meta({ id: "<Name>" })`, generated with Zod v4's native
  `z.toJSONSchema`. Cross-references between them use real `$ref`s to each other's `$id`
  (`https://ibook.dev/schemas/<Name>.schema.json`) rather than being inlined.

Both are written with 2-space indentation, LF line endings, a trailing newline, and recursively
sorted object keys (arrays keep their source order) — see
`apps/api/src/openapi/canonical-json.ts` — so a real content change is the only thing that shows
up in a diff.

## Regenerating

```
pnpm openapi:generate   # builds apps/api, then writes docs/openapi/
```

Run this after adding or changing any route schema, then commit the result. The generator
deletes any `schemas/*.schema.json` file that no longer corresponds to a registered schema, so a
removed component doesn't leave a stale file behind.

## Drift check (CI gate)

```
pnpm openapi:check
```

Rebuilds the document and schemas into a throwaway temp directory and diffs them against the
committed files here — it never writes into this directory, so a failing check leaves the
working tree untouched. Exits non-zero with the list of differing/missing/stale files if
`docs/openapi/` doesn't match what the current Zod schemas would generate. This is slice 1.6's CI
gate (`docs/PLAN.md` stage 1.6).

## How to add a new route with a schema

1. Put any schema you want to reuse (referenced from more than one route, or just worth naming)
   in `packages/protocol/src/schemas/`, tagged with `.meta({ id: "YourSchemaName", description,
   examples: [...] })`. Export it from `packages/protocol/src/index.ts`. Every route needs at
   least one `examples` entry somewhere in its schemas (see `HealthResponseSchema` for the
   pattern).
2. For a write route (POST/PUT/PATCH/DELETE), the body schema must be `z.strictObject(...)` (or
   `.strict()`) all the way down — nested objects too. `assertStrictWriteSchemas` (wired into
   every `buildApp()` instance) throws at startup, naming the route, if it isn't.
3. Declare the route with `operationId`, `summary`, `tags` (reuse an existing tag or add a new
   one to `apps/api/src/openapi/register.ts`'s `tags` list), and a `response` map. Add error
   responses with `...problemResponses(401, 403, 404, ...)` from
   `apps/api/src/openapi/problem-responses.ts` (add a status's description there once if it isn't
   already listed).
4. Register the route inside an `app.register(fastifyPlugin(async (instance) => { ... }))` block
   — never call `instance.get()/.post()/...` directly on the bare `app` outside a `.register()`
   call. `@fastify/swagger`'s schema capture depends on registration order (Fastify/avvio run
   `.register()` calls in the order they were queued); an unwrapped route added after
   `registerOpenApiDocument(app)` runs before swagger's hook exists and silently vanishes from
   the document. See the ordering comment in `apps/api/src/app.ts` for the concrete failure mode
   this avoids.
5. Run `pnpm openapi:generate`, review the diff in `docs/openapi/`, and commit it alongside the
   route.
